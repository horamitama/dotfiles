# famcal v0.2 仕様 — プリント → Googleカレンダー

2026-09-25 策定。前提は `famcal-v0.md`（v0.1 合格済み）。実装は Sprint 2（9/28〜10/11、8h）。

## 目的

v0.1 で「抽出できる」ことは実証済み。v0.2 が検証するのは **手数**。
Claude Code のセッション無しで、撮影から保存までを本人が単独で完結できるようにする。

**成功基準: 撮影 → 保存完了まで 60秒以内・タップ5回以内。実装が8hに収まらなければ設計が重い。**

## スコープ

### 作る
- 画像1枚 → 予定候補（複数可）の抽出
- 検証ルール V1〜V7（下記）
- 家族プロフィールによる該当判定
- 確認画面（編集可）
- Google カレンダーへの書き込み

### 作らない
- 妻の端末・TimeTree 置き換え（v1）
- 認証・マルチテナント（**自分専用。1家族ハードコード**）
- **繰り返し予定**（園のプリントに RRULE が要る予定はまず出てこない。運動会も健診も単発だった）
- 予定の編集・削除（Googleカレンダー側でやる）
- 通知（Googleカレンダー側がやる）
- 画像の保存（**ステートレス**）

**この結果 v0.2 に DB は要らない。** Neon も sqlc も goose も event_override も rrule 展開も不要。
v1 プランの重量級の構成要素は、ほぼ全てが「自前のカレンダーを持つ」ことに由来していた。

## 形態: 最小 Web 1枚

| 案 | 導線 | 確認UI | 判定 |
|---|---|---|---|
| CLI | 画像をMacに送る手間 | 作れる | 実使用に耐えない |
| iOSショートカット | 最短 | **作れない** | 却下。無検証で本カレンダーに書くのは危険 |
| **最小Web** | スマホのブラウザ→カメラ起動 | 作れる | **採用** |

PWA にしてホーム画面に置けば1タップ。**v1 が Expo を選んだ理由（push の確実性）は v0.2 には存在しない**——通知は Google カレンダーがやるため。

- サーバ: Go / `net/http` / `html/template`。JSフレームワーク無し
- ホスティング: Cloud Run（ゼロスケール、状態なし）
- **DB なし**

## 抽出スキーマ

```json
{
  "source": {
    "issuer": "東近江市立能登川あおぞら幼児園",
    "issued_on": "2026-09-16",
    "doc_title": "運動会について（お知らせ）"
  },
  "candidates": [{
    "summary": "運動会（4・5歳児）",
    "dtstart": "2026-10-15T09:00:00+09:00",
    "dtend":   "2026-10-15T11:30:00+09:00",
    "all_day": false,
    "location": "能登川あおぞら幼児園 園庭",
    "printed_weekday": "木",
    "applies_to": ["4歳児", "5歳児"],
    "items": ["プログラム", "保護者リボン", "水筒", "敷物"],
    "deadlines": [{"what": "健康アンケート提出", "date": "2026-09-18"}],
    "notes": "受付9:00 / 開始9:15。園児は8:45までに登園。",
    "assumptions": ["終了時刻の記載が無いため1時間で仮置き"]
  }]
}
```

### 設計上の要点

**1. `printed_weekday` を独立フィールドで持つ。これが v0.2 の肝。**
プリントに印字されていた曜日をそのまま出させ、`dtstart` から計算した曜日と **コード側で** 照合する。
**モデルに「矛盾はあるか」と尋ねない。** 決定的に計算できることはコードでやる。
v0.1 で誤植を拾えたのは実カレンダーと機械的に突き合わせたからで、勘で気づいたのではない。

**2. `confidence` は採用しない。**
LLM の自己申告スコアは校正されておらず、閾値を引く根拠にならない。
代わりに `assumptions` / 検証 WARN の有無で確認画面の強調度を決める。

**3. `assumptions` を必ず列挙させる。**
「終了時刻が無いので1時間」のような補完は、黙ってやられると事故る。明示させて確認画面で目立たせる。

**4. `applies_to` は対象の生文字列。**
「4歳児」「3歳児（いぬ組）」等をそのまま。正規化はコード側で家族プロフィールと突き合わせる。

## 検証ルール（コード側／純粋関数／テーブルドリブンテスト）

| # | ルール | 挙動 |
|---|---|---|
| V1 | `printed_weekday` と `dtstart` の曜日が不一致 | **WARN**。両方を確認画面に出す（v0.1 の健診誤植がこれ） |
| V2 | `dtend` 欠落 | `dtstart + 1h` で仮置き、`assumptions` に記録 |
| V3 | 年の記載が無い | `issued_on` 以降で最も近い該当月日を採用。1年先になるなら WARN |
| V4 | `dtstart` が現在より過去 | WARN（撮り遅れ or 年の推定ミス） |
| V5 | `deadlines` が過去 | WARN |
| V6 | `dtend < dtstart` | WARN |
| V7 | `applies_to` が家族プロフィールのどの子にも合致しない | 既定で**非選択**。候補としては残す（消さない） |

**ここが v0.2 で唯一テストしやすい純粋ロジックなので、テストを先に書く。** v0.1 の2枚を固定の検体にする。

## 家族プロフィール

```json
{"children": [
  {"name": "...", "age_class": "4歳児", "class_name": "コアラぐみ",
   "school": "能登川あおぞら幼児園"}
]}
```

JSONファイルに手書き。年度替わりに1回更新するだけなのでUIは作らない。

**v0.1 で往復が発生した唯一の原因がこれ。** 健診は3日程あり対象クラスで分岐していた。
このファイルがあれば質問ゼロで完結していた。**最優先。**

## 確認画面

- 候補ごとにカード。`applies_to` 非該当はグレーアウト＋チェック外し（V7）
- `assumptions` と WARN は黄色で強調。**特に V1 は印字曜日と実曜日を並べて出す**
- タイトル・日時・場所のみ編集可。それ以外は説明欄に流すだけなので編集不要
- 「カレンダーに追加」で選択分を一括作成
- 作成後は Google カレンダーのリンクを返す

## Claude API

- モデル **`claude-opus-5-5`**（$4/1M 入力・$20/1M 出力、1M context、既定 effort `medium`）
  - 2026-09-25 に公式ドキュメントで確認。**Opus 5（$5/$25）は legacy 扱いになった**ので使わない
  - Sonnet 5 は $2/$10 でさらに半額。**下記の比較で決める**
- 構造化出力は **`output_config: {format: {...}}`**（`output_format` は非推奨）
- thinking は **常時オン（adaptive）**。深さは `output_config.effort` で制御する
- 画像は送信前に長辺を縮小する。**iPhone の原寸（4284×5712）をそのまま投げない**（長辺1568px程度）

### コスト（旧プランの試算は誤り）

**旧プランの「1枚 $0.02」は2重に誤っていた。** ① 出力トークンの過小評価（説明欄に流す情報量が多く、v0.1 実績で1000〜1500トークン）、② **thinking トークンが出力として課金される点の見落とし**。Opus 5.5 は thinking が常時オンなので、ここは無視できない。

概算（長辺1568pxに縮小、入力 約3,200トークン／出力 thinking込み 約2,000トークン）:

| モデル | 1枚あたり | 週3枚＝月13枚 |
|---|---|---|
| Opus 5.5 (effort medium) | **約 $0.03** | **約 60円** |
| Opus 5 (effort high) ※旧案 | 約 $0.05 | 約 100円 |
| Sonnet 5 | 約 $0.015 | 約 30円 |

**承認済みの月100円枠には収まる。** ただし thinking トークン量は実測しないと分からないので、下記の比較で必ず `usage` を記録する。

### 作業1でやるモデル比較（必須）

v0.1 の2枚を固定の検体にして、**同じプロンプトで Opus 5.5 と Sonnet 5 を走らせ、抽出結果と `usage` を並べる。**

判定基準は1つ: **健診プリントの `printed_weekday`（火/木/火）を正しく写し取れるか。** ここを取り違えると V1 の誤植検出が丸ごと機能しない。プリントの文字を正確に読む能力がこのアプリの土台なので、ここで差が出なければ Sonnet 5 を採る（コストが半分）。差が出れば Opus 5.5。

**コストで先に決め打ちしない。実測してから決める。**

## Google カレンダー書き込み

- OAuth2。**自分1人なのでリフレッシュトークンを一度取得して環境変数に置く**
- テストユーザー扱いで済むため同意画面の審査は不要
- 色は **colorId 6（Tangerine）= 園の予定**（PDE=9 / ポケモン=11 / 読書=2 / 休息=8 と衝突しない）
- 既定リマインダー: 前日 + 1時間前
