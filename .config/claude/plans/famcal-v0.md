# famcal v0 — プリント抽出だけを検証する

2026-09-24 策定。旧 v1 プラン（`glistening-riding-donut.md`）は保留。

## v0 の目的

**作るのは製品ではなく、仮説の検証装置。**

検証する仮説はひとつだけ:

> 学校・保育園の日本語プリントを撮影して、Claude が予定として使える精度で
> 抽出できるか。撮影から保存まで実用的な手数で終わるか。

これが No なら famcal は存在理由が無い。**だから他の何より先にやる。**
逆に Yes が出るまで、サーバもアプリもデータベースも1行も書かない。

## やらないことの明示

v1 プランから以下を**全て落とす**。v0 の結果が出るまで復活させない。

- Expo / React Native（未経験。通知が要るのは v1 であって v0 ではない）
- Go API / Cloud Run / Neon / 4テーブル / sqlc / goose
- 招待コード認証・端末トークン
- 繰り返しの3分岐・`event_override`・展開ロジック
- 月表示 UI
- ローカル通知
- Apple Developer Program（$99）

置き換え先は**既存の Google カレンダー**。妻への共有は TimeTree の
「OSカレンダーの予定をコピー」で既に経路がある（`project_calendar_sync` 参照）。
完全自動ではないが v0 では十分。

## 段階

### v0.1 — 精度検証（コード0行）
実物のプリントを数枚撮り、Claude に読ませて抽出結果を目視で採点する。
Claude Code のセッションと Google Calendar MCP で完結するので**実装不要**。

見るところ:
- 日付（年が書かれていないプリントの年推定、「◯月◯日（水）」形式）
- 時刻（「14:00〜」「午後2時」「集合13:45」の揺れ）
- 持ち物・提出物を予定に落とせるか
- 複数予定が1枚に載っている時の分割
- 誤抽出の種類と頻度（幻覚か、読み落としか）

**合否基準を先に決める:** 1枚あたり手直し30秒以内で保存できるなら Yes。
それを超えるなら、手入力とコストが変わらないので v1 に進まない。

### v0.2 — 手数の検証（着手はv0.1がYesの時だけ）
撮影から保存までの導線を最短にする。候補:
- iOS ショートカット（共有シート → API → Google Calendar）
- 最小の Web 1枚（アップロード → 確認 → 書き込み）

ここで初めてコードを書く。言語は Go。**1スプリント以内に収まらないなら設計が重い。**

### v0.3 — 日常使用
自分の家庭で運用する。手放せないかどうかを見る。
ここまで来て初めて v1（妻の端末に置く＝Expo とサーバ）を検討する。
